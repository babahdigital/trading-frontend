# Internationalization (i18n) Guide

## Overview

Bilingual platform: Indonesian (id) and English (en). Indonesian is the source of truth -- English is auto-translated.

- Library: `next-intl` 4.x
- Locales: `['id', 'en']`, default: `id`
- Translation keys: 3100+ leaves across 21+ namespaces
- Config: `src/i18n/config.ts`

---

## Source of Truth

```
src/i18n/messages/
  id.json    <-- SOURCE OF TRUTH (manually maintained)
  en.json    <-- AUTO-TRANSLATED (via OpenRouter)
```

**Rule**: Always edit `id.json` first. Never edit `en.json` directly -- it will be overwritten by the next sync.

---

## Auto-Translation Pipeline

### CLI Tool: `scripts/translate-i18n.ts`

```bash
npm run i18n:sync          # Translate new/changed keys (incremental)
npm run i18n:sync:force    # Force re-translate ALL keys
npm run i18n:sync:dry      # Preview changes without writing
```

### How It Works

```
id.json (source)
  |
  v
Diff: find keys in id.json missing from en.json
  |
  v
Batch keys into translation requests
  |
  v
OpenRouter (DEFAULT_MODEL = Gemini 3.1 Flash Lite)
  |  System prompt: fintech/trading context, professional tone
  v
en.json (target) -- updated with translations
```

- Incremental by default: only translates new or changed keys
- Force mode re-translates everything (useful after model upgrade)
- Dry run shows what would change without writing

## CMS i18n Auto-Sync Worker

`src/lib/workers/cms-i18n-sync.ts` -- runs every 5 minutes in production.

### Covered Models

| Model | Source Columns | Target Columns |
|-------|---------------|----------------|
| Faq | question, answer | question_en, answer_en |
| PricingTier | name, subtitle, features | name_en, subtitle_en, features_en |
| LandingSection | title, subtitle, content | title_en, subtitle_en, content_en |
| Article | title, excerpt, body | title_en, excerpt_en, body_en |
| PageMeta | title, description, ogTitle, ogDescription | *_en equivalents |

### Staleness Detection

Each bilingual model has an `en_synced_at` timestamp:

```
If updatedAt > en_synced_at  -->  English translation is stale
If en_synced_at IS NULL      -->  English never translated
```

The worker queries for stale rows, translates via OpenRouter, updates `*_en` columns, and sets `en_synced_at = now()`.

### Zero-Touch Workflow

1. Admin edits Indonesian content in CMS
2. `updatedAt` automatically updates (Prisma `@updatedAt`)
3. Worker detects `updatedAt > en_synced_at` within 5 minutes
4. Auto-translates to English
5. No manual action required

## How to Add New Translations

### Step 1: Add Key to id.json

```json
{
  "pricing": {
    "new_feature_label": "Fitur Baru"
  }
}
```

### Step 2: Auto-Translate

```bash
npm run i18n:sync
```

This generates the English equivalent in `en.json`:

```json
{
  "pricing": {
    "new_feature_label": "New Feature"
  }
}
```

### Step 3: Use in Component

```tsx
import { useTranslations } from 'next-intl';

function MyComponent() {
  const t = useTranslations('pricing');
  return <span>{t('new_feature_label')}</span>;
}
```

### Step 4: Verify

```bash
npm run i18n:sync:dry  # Check parity
```

## CI Parity Gate

The CI pipeline checks that `id.json` and `en.json` have matching key counts. If a key exists in `id.json` but not `en.json`, the build fails.

This prevents deploying with missing translations.

## Locale Detection Flow

Handled in Edge middleware (`src/proxy.ts`):

```
Request arrives
  |
  v
1. URL has explicit locale prefix (/en/pricing)?
   YES -> use that locale, skip detection
  |
  v
2. NEXT_LOCALE cookie exists?
   YES -> use cookie value, skip detection
  |
  v
3. Read CF-IPCountry header (Cloudflare)
   Country = ID -> locale = id
   Country = other -> locale = en
  |
  v
4. CF-IPCountry missing? Fallback to ipapi.co
   (src/lib/geoip/fallback.ts, cached, 1.5s timeout)
   Country = ID -> locale = id
   Country = null (detection failed) -> locale = id (default to platform audience)
   Country = other -> locale = en
  |
  v
5. Set NEXT_LOCALE cookie (1 year TTL)
   ID visitors: no URL rewrite (default locale)
   Non-ID visitors: redirect to /en{pathname}
```

### Cookie Properties

| Property | Value |
|----------|-------|
| Name | NEXT_LOCALE |
| Max-Age | 365 days |
| Path | / |
| SameSite | Lax |
| Secure | Production only |

### User Locale Preference

The `User` model has a `locale` field (default `id`). On login, the `NEXT_LOCALE` cookie is set to the user's preference, making it persistent across devices.

Updatable via `/portal/account/profile`.

## next-intl Configuration

```
src/i18n/
  config.ts       # locales: ['id', 'en'], defaultLocale: 'id'
  navigation.ts   # i18n-aware routing helpers
  request.ts      # next-intl server request configuration
```

Middleware configuration in `proxy.ts`:

```typescript
const intlMiddleware = createIntlMiddleware({
  locales,
  defaultLocale,
  localePrefix: 'as-needed',   // /en/pricing (English), /pricing (Indonesian)
  localeDetection: false,       // URL is single source of truth
});
```

`localeDetection: false` prevents next-intl from reading NEXT_LOCALE cookie and auto-rewriting URLs -- our geo-IP middleware handles detection instead.

## URL Semantics

| Locale | URL Pattern | Example |
|--------|-------------|---------|
| Indonesian (default) | No prefix | `/pricing`, `/research` |
| English | `/en/` prefix | `/en/pricing`, `/en/research` |

Auth, admin, and portal pages are locale-agnostic (no prefix). Locale set via cookie/user preference.

Legacy locale-prefixed auth paths redirect: `/en/login` -> `/login` (308 redirect).
